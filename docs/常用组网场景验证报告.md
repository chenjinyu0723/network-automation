## 1. 三角三层 OSPF

拓扑为 SW1、SW2、SW3 三角互联。SW1 使用 `GE0/0/1` 连接 SW2、`GE0/0/2` 连接 SW3，地址分别为 `10.0.12.1/30`、`10.0.13.1/30`；OSPF 进程为 1、Area 为 0、Router ID 为 `1.1.1.1`。

真实模型生成并通过证据绑定编译的 SW1 命令为：

```text
system-view
interface GE0/0/1
undo portswitch
ip address 10.0.12.1 255.255.255.252
quit
interface GE0/0/2
undo portswitch
ip address 10.0.13.1 255.255.255.252
quit
ospf 1 router-id 1.1.1.1
area 0
network 10.0.12.0 0.0.0.3
network 10.0.13.0 0.0.0.3
return
```

审阅结论：接口范围、`undo portswitch`、/30 掩码、OSPF wildcard mask 均正确；没有使用未连线端口、VLAN、Trunk 或 SSH 命令。建议验收命令是 `display ospf 1 peer` 和 `display ospf 1 routing`。

## 2. 双站点静态路由

SW1 与 SW2 通过 `GE0/0/1` 点对点互联。SW1 需配置 `10.0.12.1/30`，对端为 `10.0.12.2/30`；SW1 到 SW2 后方 `192.168.20.0/24` 的下一跳为 `10.0.12.2`。

首次草案只生成静态路由时，独立审阅节点准确拒绝，指出缺少三层口转换和接口地址。修订节点接收该反馈后，真实模型生成并获独立审阅批准：

```text
system-view
interface GE0/0/1
undo portswitch
ip address 10.0.12.1 255.255.255.252
quit
ip route-static 192.168.20.0 255.255.255.0 10.0.12.2
return
```

手册证据分别绑定到 `interface`、`portswitch`、接口视图 `ip address`、`ip route-static`。验收命令为 `display ip interface brief`、`display ip routing-table 192.168.20.0 24`。

## 3. 双链路 LACP + MSTP

SW1 与 SW2 的 `GE0/0/1`、`GE0/0/2` 组成 `Eth-Trunk 1`，使用 LACP 静态并启用 MSTP。真实模型生成并由独立审阅批准的 SW1 命令为：

```text
system-view
interface Eth-Trunk 1
mode lacp-static
quit
interface GE0/0/1
eth-trunk 1
quit
interface GE0/0/2
eth-trunk 1
quit
stp enable
stp mode mstp
return
```

审阅结论：`mode lacp-static` 位于 Eth-Trunk 视图，两条成员口均来自已绘制拓扑，未夹带 VLAN、三层地址、SSH 或其它端口。建议验收命令为 `display eth-trunk 1`、`display stp brief`。

## 4. 双接入双 VLAN 三层互通

拓扑为 PC1/PC3 使用 VLAN 10、PC2/PC4 使用 VLAN 20；SW1、SW2 为接入交换机，SW3 为三层核心。接入口和上联均来自拓扑连线。

已通过 `test_multi_vlan_intervlan_compiles_access_trunk_and_vlanif_from_drawn_topology`：

- SW1、SW2：创建 VLAN 10/20；PC 直连口配置为 Access；上联配置为 Trunk 并放通 VLAN 10/20。
- SW3：创建 VLAN 10/20；两条下联为 Trunk；创建 `Vlanif10`、`Vlanif20` 并配置 `10.10.10.1/24`、`10.20.20.1/24` 网关。

该场景使用华为 VRP VLAN 专用编译器，根据拓扑确定端口角色和地址；LLM 只选择手册命令证据，不能自行改变 Access、Trunk、VLAN 或 VLANIF 的结构化事实。

## 5. 双核心 VRRP 网关冗余

设 Core1 与 Core2 已完成二层承载。VLAN 10 的终端网段为 `192.168.10.0/24`，Core1 本机地址为
`192.168.10.2/24`，Core2 本机地址由其独立配置为 `192.168.10.3/24`；共享虚拟网关为
`192.168.10.1`，VRID 为 `10`，Core1 优先级为 `120`。

真实模型 `deepseek-v4-flash` 开启 thinking 后生成下列 Core1 命令，独立审阅结论为 `approve`：

```text
system-view
vlan batch 10
interface Vlanif 10
ip address 192.168.10.2 255.255.255.0
vrrp vrid 10 virtual-ip 192.168.10.1
vrrp vrid 10 priority 120
return
```

命令均绑定到 CHM 中的 `vlan batch`、接口视图 `ip address`、`vrrp vrid`、
`vrrp vrid priority` 手册页。它没有生成物理接口、Trunk、SSH、路由协议或 Core2 的命令。验收命令为：

```text
display vrrp interface Vlanif 10 verbose
```

该场景同时暴露并修复了两个实现问题：命令页选择器此前可能误选 `ip address bootp-alloc`，现已限定为
接口视图静态 `ip address` 页；通用编译器此前把 `vrrp vrid 10 priority 120` 错判为与
`vrrp vrid priority` 手册页不匹配，现按手册命令关键字序列验证，允许参数位于固定关键字之间。

## 6. 双链路 LACP 三层 Eth-Trunk

测试要求 SW1 的 `GE0/0/1`、`GE0/0/2` 加入 `Eth-Trunk 10`，启用 LACP 静态；仅逻辑聚合口转换为三层口并配置
`10.0.12.1/30`，成员口不得配置 IP。

前两次真实调用发生了模型结构化输出波动，未返回可解析的 `command_plan`。为定位问题，隔离探针保存了原始输出：
后续采样的命令选择本身正确，但存在两个可静态判定的错误：从 `Eth-Trunk` 视图进入成员口前缺少 `quit`，并将拓扑输入的
`GE0/0/1`、`GE0/0/2` 扩写为 `GigabitEthernet`。系统现将这两项静态错误回灌给模型进行一次有界重写。

修订后的真实模型输出、手册证据编译和独立审阅均通过，最终 SW1 草案为：

```text
system-view
interface Eth-Trunk 10
mode lacp-static
undo portswitch
ip address 10.0.12.1 255.255.255.252
quit
interface GE0/0/1
eth-trunk 10
quit
interface GE0/0/2
eth-trunk 10
quit
return
```

编译器对 Huawei VRP 已要求接口视图间显式 `quit`，并保持用户在拓扑中填写的物理端口写法；Cisco 等其它方言仍允许其手册
定义的端口缩写。验收命令为 `display eth-trunk 10`、`display ip routing-table 10.0.12.0 30`。

## 7. 双机 iStack 环形堆叠

测试使用两台已确认支持 iStack 的 S5700；当前 Member1 以 `10GE1/0/1`、`10GE1/0/2` 分别组成 Stack-Port 1、2，
并设置成员 1 的优先级为 `150`。模型正确生成了：进入 `stack` 视图、`stack member 1 priority 150`、两条成员口的
`stack-port 1`/`stack-port 2` 以及只读 `display stack*` 验收命令；也正确声明优先级重启后生效，并没有生成
`save`、`reset`、`reboot` 或非拓扑端口。

首次草案创建逻辑接口时输出了：

```text
interface stack-port 1/1
interface stack-port 1/2
```

这与本手册 `stack-port` 页给出的 `interface stack-port 1` 示例、Stack-Port 编号 `1~2` 的约束不一致。系统现会从已选
手册证据的示例中抽取虚拟接口编号形式并拒绝该写法，再将错误反馈给模型重写。

修订模型已改为 `interface stack-port 1`、`interface stack-port 2`。它把 12 条 invocation 放在同一个 operation，
超过了 Schema 的单操作上限 8；这是分组错误而非命令错误。解析器现只会按原始顺序把过长 operation 拆成 `8 + 4`，不修改
任何 CLI、参数或拓扑事实。拆分后的真实独立审阅结论为 `approve`，最终草案为：

```text
system-view
stack
stack member 1 priority 150
quit
interface stack-port 1
quit
interface stack-port 2
quit
interface 10GE 1/0/1
stack-port 1
quit
interface 10GE 1/0/2
stack-port 2
return
```

这仍是配置草案：手册明确优先级变更需要重启后生效，实际实施前必须确认两台设备、版本、光模块/线缆和 iStack 兼容性；本次
验证没有连接设备，也没有执行保存或重启。

## 检索与修订观察

1. 混合检索已同时使用 SQLite FTS5、精确命令名、精确语法 token 与本地 Embedding 分支。`interface`、`ip address` 等短命令不会再被大量部分匹配页面在 `LIMIT` 前挤出候选集。
2. 主动检索在模型过早声称“证据充分”时，会继续覆盖尚未搜索的意图检索词，最多三轮。
3. 通用命令编译器要求每条 CLI 绑定当前手册 `command_id`，并限制物理接口只能来自当前设备的已连线、未受保护端口；保存、重启、删除等维护命令禁止生成。
4. 独立审阅拒绝时，通用能力会进行一次有界自动修订。修订仍必须通过手册证据、端口范围和用户最终审阅，绝不自动下发。
5. 如果命令计划本身不符合 JSON Schema，会额外触发一次不启用 thinking 的格式修复节点。该节点只能整理既有草案，
不能引入设备、端口、VLAN 或命令事实；修复后仍需经过同一套编译和审阅。对于仅因单个 operation 超过 8 条 invocation
而失败的合法 JSON，解析器会确定性按顺序拆分 operation；不会删除或改变任何 CLI。
6. 通用手册编译器会使用已检索命令页的示例校验相同虚拟接口类型的编号形式。例如当前手册出现
`interface stack-port <整数>` 时，`interface stack-port 1/1` 会被拒绝并触发一次有界重写。

## 已知边界

- 本报告验证的是规划和命令正确性，不等同于现场设备验证。`undo portswitch` 可能影响现有二层业务，应由用户确认实际端口状态后再逐台下发。
- 当前本地模型在较长、含歧义的中文描述上仍可能把“配置地址”误读成“已配置”。已在意图、规划和审阅提示中增加明确规则，并通过审阅反馈修订场景验证；后续应持续积累真实任务回归集。
- 多设备任务的自然语言要求必须明确说明每台设备角色。系统会为每台交换机生成草案，审阅节点会识别“仅应在 SW1 配置却生成到 SW2”的错误，但用户仍应检查每台设备计划。
- iStack、IRF、MLAG 等依赖设备硬件、软件版本和物理连接方式的能力，不能只根据系列名或通用 `interface` 页面判定正确。
  应在手册注入时把专用接口、命名示例、前置条件提取为结构化约束，并在配置前要求用户确认兼容性。

### 本轮修订

1. 当检索无直接证据、模型 JSON 不合规或证据绑定失败时，规划器保留可编辑的 CLI 草案并标记“未验证”，不会清空命令面板；只有手册、拓扑或审阅明确证明错误的具体 CLI 会被精确移除。
2. 检索先执行命令名精确命中与 SQLite FTS5；只有存在证据缺口时才对小批量查询调用 Embedding。精确命令标题会在主动检索模型的模糊候选之前进入证据包，避免被同主题页面挤出。
3. LLM 首次请求同时发送 `chat_template_kwargs.enable_thinking` 和 `thinking.type`；不兼容的端点再按单字段和标准兼容模式重试。HTTP 固定 `verify=False`，未设置应用层墙钟超时。
4. iStack 首轮发现两类问题：审阅文本要求“删除” Trunk CLI 时，补全器曾错误将其重新加入；以及 `stack member` 精确手册页可被模糊候选挤出。现已将删除语义排除出补全路径，并把精确手册标题优先放入证据包。最终 iStack 复测 2/2 通过。
